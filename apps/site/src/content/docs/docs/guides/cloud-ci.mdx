Smithers Cloud dispatches repository workflows from matching events and runs their jobs on its sandbox plane. A job runs the `PACKAGE.ts` target graph with `smthrs ci <pattern>`, which runs build, test, lint, and docs targets with normal cache reuse. To start a durable flow from a job, use `smthrs flow start`.

## Cloud workflows

| Surface | Behavior |
| --- | --- |
| Definitions | Repository workflows loaded for the event's source commit. |
| Admission | Matching events create durable workflow runs and tasks. |
| Execution plane | Every CI run is created on the sandbox plane. Agent runs use the separate agent plane. |
| Job environment | NixOS VM jobs use the repository's registered closure image or the platform base closure. A repository does not need its own `.smithers/environment.nix`. |
| `runs-on` | Workflow metadata; it cannot select another execution plane. |
| Caches and artifacts | Jobs get credentials scoped to their repository, run, and task. These are separate from the target action cache and the flow engine's step cache. |
| Completion | The terminal publisher updates the commit status and the `smithers / <workflow name>` GitHub check, emits `workflow_run`, and dispatches eligible downstream workflows. |

This repository's [`.smithers/workflows/ci.tsx`](https://github.com/smithersai/smithers/blob/main/.smithers/workflows/ci.tsx) declares push-to-main and manual triggers; its task groups invoke [`scripts/ci/cloud.sh`](https://github.com/smithersai/smithers/blob/main/scripts/ci/cloud.sh).

The owning code is in [`packages/backend/internal/services`](https://github.com/smithersai/smithers/tree/main/packages/backend/internal/services): `workflow_nix_ci.go` and `workflow_run_terminal.go`.

### Verify a Cloud run

Inspect the run ID, tested commit, task results, and terminal status, then the GitHub check when the repository requires one. A queued run, accepted dispatch, or in-progress check is not completion; cancellation is not failure. Publication errors are logged, so confirm the check's completed result before making it required.

For scheduled flows, use the app's [Dispatcher](/docs/app/dispatcher/), or host the scheduler yourself with `smthrs serve`; see [Define triggers](/docs/guides/triggers/).

## Launch a flow from a CI job

Commit flow sources under `flows/` and configure their model seats. The job needs Node.js <code>{versions.nodeRange}</code> and the [Smithers CLI](/docs/installation/#install-the-cli). Expose only the provider credentials the flow's seat needs, from the CI system's secret store.

```bash
smthrs flow start deploy/status --format json
```

Replace `deploy/status` with your flow. `flow start` approves its launch with run scope and does not prompt, so use it only for work the pipeline is authorized to run. On failure, list the runs before the job exits:

```bash
smthrs runs list --format json
```

A fresh checkout has no `.flows/` history. Work that must survive the job belongs on a persistent host.

### Handle the exit status

A local attached launch exits `0` when the run completes, `1` when it fails, `3` when it waits for approval, and `130` or `143` when it is interrupted. See [exit codes](/docs/reference/errors/#exit-codes). A read such as `runs show` exits by whether the read succeeded, not by the run's outcome.

If the flow parks on exit `3`, either treat it as a failed requirement and change the flow so the job needs no human answer, or run the work on a persistent [control plane](/docs/guides/control-plane/), approve it there, and resume the same run. A remote launch returns an admission receipt, so the pipeline must inspect that run's completion itself.

### Keep failure evidence

```bash
smthrs runs show <run-id> --format json
smthrs runs logs <run-id> --limit 100 --format jsonl
```

Save the output with the CI system's artifact facility. Log exports help diagnosis but cannot resume a run; for resumable state, see [Back up and retain run state](/docs/guides/retention/).
