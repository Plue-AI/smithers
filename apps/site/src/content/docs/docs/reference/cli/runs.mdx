`smthrs runs` operates executions already stored in a project. Supply the run ID returned at launch or shown by `runs list`.

## Read current state

| Command | Result |
| --- | --- |
| `runs list [--flow <id>] [--status <status>]` | Matching durable runs. |
| `runs show <run>` | Current run state and an event-derived diagnosis. |
| `runs output <run> [node]` | Recorded node outputs; `result` selects the final assistant output. |
| `runs devtools <run> [node]` | The run's node tree with state and timings, and one node's inputs, outputs and journal frames. |
| `runs logs <run>` | Recorded events, optionally followed live. |

A successful read does not imply that the run succeeded. Read its status field. `runs show` prints a diagnosis card: `Verdict`, `Run`, `Activity`, `Tokens`, up to three `Refusals`, then `Cause`, `Output`, and `Unblock` when they apply, and a `Next` line. Use `--format json` for structured state and `--format jsonl` for event streams.

## Control an execution

| Command | Effect |
| --- | --- |
| `runs resume <run>` | Re-drives an existing execution from persistent state. |
| `runs cancel <run>` | Requests cancellation of one run. |
| `runs cancel-all` | Cancels all nonterminal runs in the selected project. |
| `runs signal <run> <payload>` | Delivers a JSON object containing the signal name and payload. |
| `runs steer <run> --message <text>` | Sends new steering instructions. |

Use each command's `--help` or `--schema` for its exact arguments. [Steer a run](/docs/guides/steering/) explains the difference between steering, signals, and cancellation.

## Receipts and exit codes

Control commands print one receipt: `Accepted`, `AlreadyApplied` (an identical signal was already delivered), `Parked`, `Conflict`, or `Terminal` with the status of a run that had already settled. The exit code follows the receipt: `Terminal` cancelled exits `130`, `Terminal` failed or `Conflict` exits `1`, `Parked` exits `3`, and the rest exit `0`. So `runs cancel` exits `130` once the run is cancelled.

`runs steer` mints a fresh message id per call, so two calls deliver two messages. `runs output` names nodes `<flow>#<n>` plus `result`; a call that never settled is `pending`. `runs logs` prints a transcript with one `=== turn N ===` header per model turn; `--follow --format jsonl` prints one event per line.

Current-state commands accept the connection options `--root` and `--remote`, and read the bearer from `SMITHERS_TOKEN`. The saved `smithers auth login` session is shared with repository commands; `SMITHERS_TOKEN` is the non-interactive override. Historical operations below require the local host that owns the run state.

## Inspect history

`runs inspect <run> [--at <sequence>]` derives state and event counts at a frame. `runs replay` also reads recorded history and sealed results. Neither executes action code. Omitting `--at` selects the latest frame.

`--lineage` selects a lineage explicitly. `--limit` bounds journal entries read, defaulting to 10,000 for these CLI history commands.

## Verify against current code

`runs verify <run>` reports what `runs resume` would do under the flow code now on disk, before anything runs. It resumes a copy of the project's stores with an engine that executes no action code, and lists the recorded steps that `replayed`, the first step that would execute again (`executes`), and the recorded steps nothing asked for (`notReplayed`). It exits `0` when every recorded step replays and `1` with `run_divergent` when a recorded step would be dropped or re-keyed. The project's own stores are only read: SQLite stores are copied with `VACUUM INTO`, PostgreSQL ones into scratch schemas that are dropped afterwards.

Without a run, `runs verify` reports every run the store holds (settled runs are listed under `settled`) and exits `1` when any diverges. `--against <engine.db>` verifies the store at that path, with the `control.db` beside it, under the project's current flows.
