# C-UI-02 Product words and minimal text: a deterministic copy lint

Proves: mvp.md §2 rule 7, §3 Vocabulary, §9 Copy · spec.md §14.2, §14.3, §14.6b · Layer: unit · Stage: S1 · Tickets: T-CAT-01
Automation: `apps/app/src/mainview/cards/ProductWords.test.tsx` (new), with the rules in `apps/app/src/mainview/cards/productWords.ts` (new) and the boundary fixtures in `productWords.fixtures.ts` (new) · Runs in: CI

## Setup
- The Views in `apps/app/src/mainview/cards/views/` and their fixtures from `packages/rpc/test/fixtures/` (T-APP-19), rendered in happy-dom (an app dev dependency).
- The rule module `apps/app/src/mainview/cards/productWords.ts`: `lintCopy(root: Element): Violation[]`, `lintText(text: string): Violation[]` and the term list, exactly §14.6b's. C-CAT-03 reads the same list.
- The boundary fixtures in `apps/app/src/mainview/cards/productWords.fixtures.ts`, as plain DOM.

The rules decide from DOM text alone. Layout, fonts, viewport width and visual line wrapping never enter them.
- **R0 Scope.** Chrome text is every text node, and every `aria-label`, `title`, `placeholder` and `alt` attribute, inside a rendered View, except inside a data region: an element with `data-content`, or a `code`, `pre`, `textarea`, `input`, `kbd` or `svg` element. Data regions hold what people, agents, files or GitHub wrote: prompts, transcripts, file text, diffs, wiki pages, Markdown answers, model summaries and GitHub text quoted verbatim.
- **R1 Banned terms.** A chrome string fails when it holds one of §14.6b's terms (workflow, thread, task, lane, box, workspace, mythical, sandbox, VM, seat, profile), its plural with `s` or `es`, or `microVM`, as a whole word in any case. A word boundary is any character that isn't a letter or a digit, so "task-list" fails and "taskbar" passes.
- **R2 Block length.** A block is the nearest `p`, `li`, `dd`, `dt`, `h1` to `h6`, `button`, `a`, `label`, `td`, `th`, `[role=option]` or `[data-copy-line]` element holding the text; a block that contains another block is skipped, unless it is a `button`. Its words are the whitespace-separated tokens of its chrome text once data regions are removed. Inside a card body (`[data-card-body]`), a block holds at most 12 words. A block is not a visual line: a 12-word label that wraps passes, and a 13-word label on one line fails.
- **R3 Fixed phrases.** A chrome block fails when it contains, in any case, "not measured", "not yet measured", "generated by", "powered by", "provided by", "data from" or "source:" (AGENTS.md MINIMAL TEXT: no "not measured yet" rows, no provenance footers).
- **R4 One sentence.** A chrome block fails when it holds two sentences: a `.`, `!` or `?` followed by whitespace and a letter.
- **R5 Coverage.** Every View renders every fixture of its card, inline and maximized, in light and dark.
- `lintText` applies R1, R3, R4 and the 12-word limit to a string. Each T-APP adapter test runs it on every `Action.label`, `disabled.reason` and toast title the adapter emits.

What these rules can't decide belongs to the **copy review**, not to this check: whether a short sentence explains how the product works, whether a label reads well where it wraps at 390 px, and whether the words fit the action. The design reviewer (smithers-06) reads every View's fixture screenshots at 1,440 px and 390 px, light and dark, against §14.6b and records approve or fix per screen in the T-UI ticket's issue. C-UI-02 never passes or fails on that review.

## Steps
1. Run `lintCopy` on each boundary fixture and compare with its expected result.
2. Render every View × fixture × {inline, maximized} × {light, dark}, and run `lintCopy` on each.
3. Collect the `lintText` results from the T-APP adapter tests.
4. Read the Settings View's host label from the Settings fixture.
5. Count the renders in step 2 against Views × fixtures × 4.

## Pass when
- Step 1: every boundary fixture gives its expected result.
- Steps 2 and 3: zero violations.
- Step 4: the detected host is labeled "This Mac" (§14.3).
- Step 5: the count equals Views × fixtures × 4; nothing is skipped.
- The same DOM gives the same result at every viewport width and in both themes.

## Fail when
- A View renders lazily or behind a flag and escapes step 2.
- A banned term hides in an `aria-label`, `title` or `placeholder`, which assistive technology reads aloud.
- Settings shows "host profile" or "VM" for the detected host.
- A rule's result depends on layout, so a wrapped label changes the outcome.
- Chrome copy is wrapped in `data-content` to dodge the lint. The lint can't see this; the copy review must reject it.
