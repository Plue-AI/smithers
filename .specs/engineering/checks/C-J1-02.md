# C-J1-02 Setup card completes install setup; Source ready and Machine ready are separate

Proves: mvp.md J1.1–J1.4, §6.1, §6.3 (squash check), M-28 · spec.md §16.2, §16.3, §1.4, §5.1.0, §6.3 (`/api/install`), §7.2 (`install`), §8.2.1, §10.6.2, §12.1, §14.3 (Setup), §19.3 · Layer: e2e · Stage: S1 · Tickets: T-INS-06, T-APP-03
Automation: `apps/app/e2e/real/setup.spec.ts` (new) · Runs in: reference host

## Setup
- Reference host with no `$STATE` (fresh install) at the commit under test; `smthrs host start` done, its printed setup URLs recorded.
- A second Mac B on the same LAN.
- Scratch repository `smithers-mvp-canary/<date>`, owned by `canary-owner`, with squash merging **disabled**; `canary-owner` has admin on it.
- Model keys: one invalid coding provider key, one valid coding provider key, one valid Cerebras key for the `fast` role, one valid AI Gateway key for `jev`. No ChatGPT sign-in.

## Steps
1. Open `http://localhost:4000/setup` without the token, then the printed setup URL. Record the Setup card and `GET /api/install`.
2. Step 0, Address: set the bind address `0.0.0.0` and the origin `http://<mac>.local:4000`, and confirm.
3. On Mac B, open the setup URL printed for the LAN listener at `http://<mac>.local:4000`. Continue every later step from B.
4. Enter the scratch repository. Create the GitHub App (manifest flow) and confirm once on GitHub. Record the App's permissions, callback URLs and webhook state on GitHub.
5. Install the App on the scratch repository.
6. Read the squash row. Enable squash merging on GitHub through the row's link, then return.
7. Sign in as `canary-owner`. Then open the same setup URL in a private window.
8. Model access: paste the invalid coding key, then the valid one; paste the fast-model key and the AI Gateway key; skip ChatGPT.
9. While the mirror runs, reload the page once. Record the row states before and after.
10. Watch Source ready, then Machine ready. Record each row's first render time and the matching event time from `GET /api/install`.
11. Repeat step 9 during the image build, then kill the host service (`launchctl kickstart -k`) and reload after it restarts.

## Pass when
- Without the token, the card offers no claim. With it, step 7 makes `canary-owner` the owner and deletes the token, so the second use of the URL is refused (§5.1.0).
- Address is step 0, and step 1 (Create the GitHub App) stays disabled until it is done (§16.2).
- The App is owned by `canary-owner` (§12.1.1) and has contents, workflows, pull_requests and issues write; checks, statuses, administration, metadata and members read; an inactive webhook; and callback URLs exactly `http://<mac>.local:4000` and `http://localhost:4000` (§12.1.2). GitHub's redirect returned to B at `http://<mac>.local:4000/setup/github/callback`.
- The card shows the address and "This Mac" with its derived limits (§14.3, §8.2.1); no row depends on a VPN, proxy or public address (§1.4).
- Each row's check mark renders no earlier than its event in `/api/install`; no later step's control is enabled before the earlier step reports done.
- With squash disabled the row shows "Enable squash merging on GitHub ↗" linking the repository settings, and it checks after squash is enabled.
- Model access asks for three roles, `coding`, `fast` and `jev` (§11.5a). The invalid key keeps its field open with a reason; after saving, `flow_config` holds the three role models, and no key value appears in the DOM, the card payload or any response body in the HAR.
- Source ready renders while Machine ready still shows progress, in separate rows, with Source ready's time < Machine ready's time.
- After each reload and the restart, every finished step stays finished, no step runs twice (GitHub lists exactly one App for the install), and the build either resumes or shows its failure with Retry.

## Fail when
- Machine ready appears at the same render as Source ready, or before its event.
- The App is created before Address is confirmed, or its callback URLs miss the configured origin.
- A reload or restart creates a second GitHub App, re-runs the mirror from 0 %, or loses a saved key.
- A step shows done on a `202 requested` response (§6.2.2).
- A key value is echoed anywhere after save.
- The setup URL claims the install a second time, or a request without the token claims it.
