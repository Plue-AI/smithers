# C-J1-05 Add members by username; "needs access on GitHub"; a teammate signs in at the install's public origin

Proves: mvp.md J1.8, §6.2, §6.15 "Members and maintainers", M-05, M-28 · spec.md §1.4, §5.1.2, §5.1.4, §6.3 (`/api/members`), §14.3 (Members card), §16.3.1, §16.3.2 · Layer: e2e · Stage: S1 · Tickets: T-ACC-02, T-APP-06, T-REL-02
Automation: `apps/app/e2e/real/members.spec.ts` (new) · Runs in: reference host

## Setup
- Reference host (checks README): the team's Mac mini, whatever its size; the evidence records its host profile (§8.2.1). It runs the install at the commit under test, with setup completed through the owner claim (C-J1-02), and records `smthrs --version`.
- In Settings the owner has set a bind address and the public origin `http://<mac>.local:4000` (§16.3.1). Plain HTTP is deliberate: the app must work in an insecure context (§16.3.2).
- A scratch repository `smithers-mvp-canary/<date>` on GitHub, with the install's App installed. Three GitHub test accounts:
  - **B**: repository role `maintain`;
  - **A**: `write`;
  - **C**: no access.
- Browsers:
  - the owner's on the Mac at `http://localhost:4000`;
  - A's on a second Mac on the same network at the public origin, with a saved GitHub profile for A;
  - C's on the second Mac, with a saved GitHub profile for C.

## Steps
1. The owner runs `/members` and the Members card opens.
2. The owner adds B, then A, by GitHub username, using the keyboard only.
3. The owner adds C.
4. On the second Mac, A opens the public origin and signs in with GitHub.
5. On the second Mac, C opens the public origin and signs in with GitHub.
6. The owner changes A's role to Maintainer, then back to Member.
7. The owner opens `/members` while the backend is stopped for 10 s, then started again.

## Pass when
- Step 2: the card lists B as Maintainer and A as Member, each with their avatar and login. Each row appears within 1 s of the request completing.
- Step 3: the add is refused, and the card shows "needs access on GitHub ↗" linking to the repository's collaborator settings on GitHub. No row for C exists (§5.1.4).
- Step 4: A lands in the app signed in as A at the public origin. A's role shows as Member, and A's Members card has no add, role or remove controls.
- Step 5: C is refused with the reason (§5.1.2). No session cookie is set (checked in browser storage).
- Step 6: A's role changes in the owner's card and in A's open card without a reload.
- Step 7: the card shows a typed infra failure ("not your fault") with Retry, and it never shows an empty roster as truth.
- The card shows no invitation, email or organization controls (mvp.md §6.15).

## Fail when
- A row appears before the backend confirms it.
- B seeds as Member.
- C is added to the roster.
- A must create a Smithers account, or must accept an invitation.
- The sign-in only works on `localhost`, or breaks on the plain-HTTP origin.
- The card carries explanatory prose instead of the row states (MINIMAL TEXT).
