# C-J2-05 Merge turns the TODO Merged; the issue closes only when the TODO fixes it; a learning receipt follows

Proves: mvp.md J2.6, §4.1 Merged, §6.3 (TODO merges row), M-01, M-15, rule 6 · spec.md §4.1, §4.1.3, §10.6.2, §11.8.1, §11.8.3, §12.3 (TODO PR merged), §12.4.1 · Layer: e2e · Stage: S1, S3 · Tickets: T-STK-04, T-FLW-06, T-REL-02
Automation: `apps/app/e2e/real/todo-merge.spec.ts` (new) · Runs in: reference host

The S1 run of this check covers merge and issue close only. Steps 6-7 and their pass conditions run from stage 3, after T-FLW-06.

## Setup
- Install from the commit under test on the reference host; record version and commit.
- Scratch repository `smithers-mvp-canary/<date>` with squash merging allowed and no branch protection.
- Owner Will signed in with a browser session.
- Issues #7 and #8 by Ben. T1 made from #7 with fixes on; T2 made from #8 with fixes off. Both reach `in_review` with green checks; T1 is first in the stack.

## Steps
1. Will opens T1's TODO card, reads the evidence, and selects **Merge** (the request carries the PR head he saw).
2. Read GitHub: the PR's merge method and commit, and `main`'s log.
3. Read T1's state over time, and issue #7.
4. Will merges T2 the same way.
5. Read issue #8. Before steps 1 and 4, at each reviewed SHA set required checks passed and one optional check failed. Exercise step 1 through the TODO Container and step 4 through a delegated merge request followed by the person’s Confirm Container. Before each press, set a required check pending and try both doors; then pass it without changing the SHA and complete the merge.
6. (S3) Wait for the learning run admitted after T1's merge to finish; read the Home card's background runs.
7. (S3) Read T1's TODO card.

## Pass when
- Step 2: the PR merged by squash; `main` gains exactly one commit for T1, whose tree equals the reviewed head's tree.
- Step 3: T1 shows `merged` only after GitHub reports the merge and `main` contains the commit; no earlier frame shows Merged. Merged appears within 60 s of GitHub's merge (§12.2.3).
- Step 3: issue #7 is closed by the App with a comment linking the change.
- Step 5: issue #8 stays open.
- Steps 1 and 4: one `todo_approvals` row per merge with Will, the session credential and the merged head SHA. Both TODO and Confirm display the required/optional distinction, allow the failed-optional/passed-required case, and block pending-required with its reason and zero GitHub merge calls. The service independently refuses a direct pending-required merge request. Repeating at a new SHA requires checks for that SHA.
- Step 6 (S3): the learning run shows as a background run, never as a TODO.
- Step 7 (S3): T1 shows a receipt "N lessons" with N ≥ 1 that opens the wiki pages or proposal; T1's state is still `merged`, and no `todo_events` row changes it.

## Fail when
- Merged appears before `main` contains the commit (an optimistic state).
- A merge commit or rebase merge is used instead of squash.
- Issue #8 closes although T2 doesn't fix it (today's `complete` closes every linked issue).
- (S3) Learning changes T1's state or adds a revision.
