# C-J11-04 Thrashing is flagged deterministically

Proves: mvp.md §6.14 (Monitor, Thrashing) · spec.md §11.6.4 · Layer: integration · Stage: S1 · Tickets: T-FLW-07, T-REL-02
Automation: `packages/backend/internal/services/run_thrash_integration_test.go` (new) · Runs in: CI (real PostgreSQL, recorded `todo` run journals)

## Setup
A TODO T4 whose recorded attempt fails `TestRetryBackoff` three times in a row, each failure naming `retry.go`, with no edit to `retry.go` in between. A second journal is the same except the agent edits `retry.go` after the second failure. A third journal fails the same test twice in attempt 1 and once in attempt 2.

## Steps
1. Deliver the first journal through the production authenticated run-event ingest wired by the install composition, not a direct detector call; use fixed journal and projection fixtures.
2. Read `todo:4` and `run:<id>` from the live channel.
3. Replay the second and third journals for T5 and T6.

## Pass when
- After the third failure, `todo:4` carries the indicator "Thrashing: TestRetryBackoff failed 3×", and the failing phase on `run:<id>` has tone `thrash`.
- T5 and T6 carry no thrash indicator.
- A later passing run of the check clears T4's indicator.
- Replaying the same journal twice gives identical projections.
- No model call is recorded for the detector.

## Fail when
- The indicator fires on fewer than 3 failures, across attempts, or after a named file was edited.
- The indicator changes the run's state or steps.

## Evidence
`.artifacts/checks/C-J11-04/<ts>/`: the three journals, the projected `todo` and `run` payloads, the test log and the commit.
