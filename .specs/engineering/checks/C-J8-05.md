# C-J8-05 The next plan follows an edited decision

Proves: mvp.md J8.2–J8.3, §12 item 1 ("the next related plan following that exact revision"), §6.11 One vault for both agents, §6.9 Works TODOs · spec.md §10.4.1, §13.2, §13.4, §15.1.2 · Layer: e2e · Stage: S3 · Tickets: T-FLW-10, T-COL-09
Automation: `apps/app/e2e/real/wiki-decision-follow.spec.ts` (new) · Runs in: reference host, with the install's real coding and fast models

## Setup
- Install at the commit under test. Ben (maintainer) and Alice (member) signed in on two browsers.
- Scratch repository `smithers-mvp-canary/<date>`: `src/webhooks/retry.ts` exports `retryExponential()` and `retryFixed(delayMs)`, and nothing calls either; `src/webhooks/deliver.ts` has `deliver()` with no retry; `test` and `lint` scripts pass.
- Wiki page `decisions/webhook-retries` at revision 1: "Decision: webhook redelivery uses `retryExponential()`. Reason: provider rate limits."
- The run repeats 3 times, each on a fresh scratch repository and install data directory.

## Steps
1. Control: create TODO T1 "Retry failed webhook deliveries in deliver.ts". Let its plan step finish. Read T1's plan receipt and plan text, then drop T1.
2. Ben and Alice open the page together. Alice replaces the decision with "Decision: webhook redelivery uses `retryFixed(5000)`. `retryExponential()` is not used for webhooks. Reason: the provider's idempotency window." Ben types in another paragraph while she edits. Wait for the stored revision.
3. Create TODO T2 with T1's prompt. Let it reach In review.
4. Read T2's plan receipt, plan text and PR diff.

## Pass when
- Control: T1's receipt cites `decisions/webhook-retries` at revision 1, and T1's plan names `retryExponential`.
- T2's receipt cites the page at the revision step 2 stored, with that revision's digest, and cites no earlier revision.
- T2's plan names `retryFixed` and doesn't propose `retryExponential`.
- T2's PR diff calls `retryFixed(5000)` from `deliver.ts` and adds no call to `retryExponential(`.
- All of the above hold in 3 of 3 runs.

## Fail when
- T2 cites the new revision but its change follows the old decision (cites without following).
- T2 cites revision 1, or a revision older than the one the edit stored.
- The control already uses `retryFixed`. The run proves nothing: fix the fixture and rerun; it never counts as a pass.

## Three-run driver

On the reference Mac, run `cd apps/app && bun scripts/wiki-decision-campaign.ts <prepared-installs.json> <new-evidence-directory>`.
The manifest is an array of exactly three `{stateDirectory, environment}` entries.
Each environment supplies `SMITHERS_REAL_BASE_URL`, `SMITHERS_REAL_E2E_BUILD_SHA`,
`SMITHERS_JOURNEY_REPOSITORY`, `SMITHERS_JOURNEY_DATABASE_URL`,
`SMITHERS_JOURNEY_SMTHRS`, and the `SMITHERS_JOURNEY_WILL_SESSION`,
`SMITHERS_JOURNEY_BEN_SESSION`, `SMITHERS_JOURNEY_ALICE_SESSION` storage-state paths.
All installs qualify one commit; repositories, databases and declared absolute
state directories must differ. The owner prepares the installs and signs in;
the driver does not provision repositories or authenticate members.

The driver runs only this journey, once per install, with no retries. It writes
`campaign.json` only after three successful Playwright reports, with zero skipped,
flaky or failed tests. Each run retains its report and browser attachments.
The output directory must be new. Manifest paths are preparation declarations,
not proof of fresh provisioning: retain the install preparation receipts alongside
the campaign. Never commit the manifest or browser storage states.
