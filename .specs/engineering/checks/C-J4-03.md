# C-J4-03 Only the next item merges; later items say "Merges after Tn"

Proves: mvp.md §4.2 Merging, §6.6 Order, §6.10 PR card, rule 6, M-05 · spec.md §4.1.2a, §5.2, §5.2.1, §5.3, §5.4, §10.6.1, §10.6.2, §10.6.3 · Layer: integration+e2e · Stage: S1 · Tickets: T-STK-04, T-REL-02
Automation: `packages/backend/internal/services/todo_merge_db_test.go` (new) and `apps/app/e2e/real/todo-merge-order.spec.ts` (new) · Runs in: CI (integration) and reference host (e2e)

## Setup
- Integration: real PostgreSQL; the fake GitHub REST server records every request. Owner Will and Maintainer Ben have sessions; Member Alice has a session; Ben also has a delegated credential (`via=claude-code`), and the test mints a run credential (machine credentials are S2 and covered by C-ACC-02).
- Stack: T1, T2 and T3 all `in_review` with green required checks and `mergeable: true`; PR heads H1, H2 and H3. T1's PR is ready; T2's and T3's are drafts (§12.5.1).
- E2E: install from the commit under test on the reference host; scratch repository `smithers-mvp-canary/<date>`; the same three TODOs reached through the fixture `todo` flow of C-J4-02. The GitHub-sentence step needs T-GH-05.

## Steps
1. Integration: Ben (session) merges T2 with H2.
2. Ben merges T1 with a stale head H1′ while the PR head is H1.
3. Alice (session) merges T1 with H1. The run credential merges T1 with H1. Ben's delegated credential merges T1 with H1.
4. Make T1's required check fail; Ben merges T1 with H1. Restore it.
5. Open a `mythical_stacks.attention{kind: order}` row; Ben merges T1 with H1. Settle the row.
6. The fake server answers T1's next merge call with 405 `{"message":"At least 1 approving review is required by reviewers with write access."}`. Ben merges T1 with H1. Restore normal answers.
7. Ben (session) merges T1 with H1.
8. After T2 rebases onto the new `main` and its PR is force-updated to H2′ (§10.6.3), Ben merges T2 with H2, then with H2′.
9. E2E: open the Home card and each TODO card as Ben before and after merging T1.
10. E2E: enable branch protection on `main` requiring one approving review. Ben presses **Merge** on the first item. Disable it.

## Pass when
- Steps 1-5: each request is refused with the §6.2.3 envelope (`conflict` "Merges after T1" for step 1, `conflict` stale head for step 2, `permission` for Alice and the run credential, the failing check's name for step 4, `conflict` for the open attention in step 5), and the fake server records zero merge calls for them.
- Step 3, Ben's delegated credential: the response is `202 {confirmation, state: "requested"}` for a `review_merge` confirmation on Ben's `confirmations:<member>` topic, with nothing else in the body, and no merge call (§15.1.5).
- Step 6: the refusal's message is GitHub's sentence verbatim, class `github`; no generic "GitHub refused to merge (HTTP 405)".
- Step 7: exactly one `PUT /pulls/{n}/merge` with `sha = H1` and `merge_method = squash`; one `checks.Land` approval (Ben, session credential, H1).
- Step 8: the merge with H2 is refused as stale with no GitHub call; the merge with H2′ succeeds and its approval row names H2′.
- Step 9: before the merge, only T1 shows **Merge**; T2 and T3 show "Merges after T1". After it, T2 shows **Merge** and T3 "Merges after T2".
- Step 10: the TODO card shows GitHub's sentence about the required review, word for word.

## Fail when
- Any refused request reaches GitHub (a merge call in the log).
- A delegated credential merges, or receives anything beyond a confirmation id and state (§5.4).
- GitHub's own lack of order enforcement lets T2 merge first through Smithers.
- The UI hides Merge but the API accepts it (presentation-only enforcement, §5.2.1).
- A GitHub refusal shows a generic sentence instead of GitHub's text.
