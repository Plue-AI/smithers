# C-J8-02 Two people co-edit a wiki page live

Proves: mvp.md J8.2, §6.11 Pages and editing · spec.md §6.2.4, §7.4.1–7.4.4, §7.6 (row 8), §13.1–13.2 · Layer: e2e · Stage: S1 (today's protocol), S3 · Tickets: T-COL-09
Automation: `apps/app/e2e/real/wiki-coedit.spec.ts` (new) · Runs in: reference host, browsers on a second Mac on the same network at the install's public origin

## Setup

- A fresh install at the commit under test. The page `decisions/retries` has 3 earlier revisions created through the app.
- Members: Ben and Alice signed in, in two browser contexts on one Playwright runner (one monotonic clock).
- S1 run: the wiki uses today's protocol (`GET …/document`, `POST …/updates`, SSE `…/stream`).
- S3 run: the build includes T-COL-09, so the page travels on the live channel with `Y.Text("markdown")` unchanged.

## Steps

1. Both open `/wiki.page decisions/retries`.
2. Ben types 200 characters in one paragraph while Alice types 200 in another, both at 8 per second. Record each character's arrival in the other page.
3. Both type 30 characters at the same position at the same time.
4. Block Alice's edit traffic with Playwright routing (the `POST …/updates` in S1, the `/api/live` socket in S3). She types 50 characters and reloads the tab. Then lift the block.
5. Stop typing for 5 s, then open the page's history.
6. S3 only:
   - call `POST …/wiki/decisions%2Fretries/updates` and `GET …/stream`;
   - search `docs/api/openapi/repositories.yaml` for both paths;
   - open revision 2 from history.

## Pass when

Both runs:
- After steps 3–4, both pages and the stored page body (`GET` through the wiki API) are byte-identical and contain every typed character exactly once. Alice's blocked characters survive the reload.
- History shows the 3 earlier revisions unchanged and readable.

S1 run:
- Step 2's latencies are recorded as p50/p95 with n = 400, as the baseline for S3. No latency gate.

S3 run:
- Step 2: each character reaches the other page in < 1 s p95, with n = 400, on the runner's clock.
- The edits of step 2 produce one revision per 2 s idle period, not one per update (§7.4.2). Each new revision names both editors.
- Step 6: both calls return 404. Neither path appears in the OpenAPI document. Revision 2 renders.

## Fail when

- A page shows the other's edits only after a manual refresh (S3).
- Pages diverge, a character is duplicated, or Alice's blocked edits vanish on reload.
- S3 writes one revision per keystroke, or loses the attribution of the second editor.
- The S3 build still serves the POST or SSE route, or keeps its OpenAPI rows (two co-editing protocols).
- Earlier revisions fail to load after the protocol change.
