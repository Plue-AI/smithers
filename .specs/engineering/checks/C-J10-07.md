# C-J10-07 Force-push to `main` gives the owner a confirmation; nothing changes before confirm

Proves: mvp.md §6.3 "`main` rewritten on GitHub" · spec.md §4.1.2a, §5.2, §6.1.2, §10.1, §10.5.1, §10.8.1, §12.3 (`main` rewritten row) · Layer: integration · Stage: S1 · Tickets: T-GH-07, T-ACC-03
Automation: `packages/backend/internal/services/github_main_pull_force_push_test.go` (new) · Runs in: CI

## Setup
- Real PostgreSQL and real git. `githubfake` serves a bare repository as GitHub over smart HTTP and logs every write.
- The install's mirror follows `main` at commit `M1`. The stack holds T1 In review (PR open, first in order, green) and T2 Working.
- Credentials: the owner's session, a maintainer's session, a member's session and a delegated credential.
- The scheduler under an injected clock.

## Steps
- Adopted T-GH-07 boundary cases: Race reset with ordinary pull and merge dispatch through production boundaries using barriers at fence verification and locked ref write. Crash before ref write, after ref write and after settlement commit before consumer dispatch; recovery admits one effective stack update and machine-only flow load. Inject a legitimate concurrent third tip and assert it remains unchanged with attention open. Owner/session and stale-tip refusals precede writes

1. Rewrite the fake's `main` to `M1'`, a commit that doesn't descend from `M1`.
2. Advance 30 s (one refs cycle).
3. Advance 10 more refs cycles. The maintainer tries to merge T1.
4. Submit **Reset to GitHub main** as the maintainer, the member and the delegated credential. Resolve the command as `main.reset-to-github` from its catalog descriptor; also try the Owner's delegated credential.
5. Rewrite the fake's `main` again to `M1''`. Submit the owner's **Reset to GitHub main** for `(M1, M1')`.
6. Submit the owner's **Reset to GitHub main** for `(M1, M1'')`.
- Send Reset with delegated credentials for each role, non-owner person sessions and an owner session with stale `(old, new)`.

## Pass when
- Reset, ordinary main pulls and merge dispatch share the repository operation serialization boundary and the existing repo-host write lock. Under that boundary, reread the attention/merge fence and reset binding before the expected-old ref write; retain the operation claim through settlement. Persist reset intent before writing. After the ref reaches new, atomically commit attention settlement, projections and durable main-moved intents keyed to that reset intent. Stack and machine-only flow-load consumers apply each intent idempotently after commit. Recovery at old keeps attention open, at new finishes settlement/intents once, and at a legitimate third tip preserves it with attention open

- After step 2: exactly one `mythical_stacks.attention{kind: force_push, old: M1, new: M1'}` row, on the Needs you card for `main` rewritten on GitHub for the owner and for no one else; no TODO has a `force_push` Needs you.
- Through step 3: the mirror's `main` is `M1`; the stack order, the `mythical` ref, TODO states, PR branches and `workflow_definitions` are byte-identical to before step 1; no flow-load run is admitted; the merge is refused with class `conflict` because the open row holds merges (§4.1.2a).
- Step 4: each request is refused with 403, and nothing changes.
- Step 5: the request is refused as stale, and the row now names `M1''`.
- Step 6: the mirror's `main` is `M1''`, T1 and T2 have `rebase_pending{onto: M1''}`, and the row is `settled` with the owner as `settled_by`.
- The fake's write log has no push to `refs/heads/main` at any step.
- Delegated=403 never/never, other roles=403 permission/permission and stale=409 conflict/stale_attention. No refused call changes the mirror or settles attention; stale attention names the current tip.

## Fail when
- The mirror resets before the owner confirms.
- The main pull keeps failing with backoff and no attention row appears.
- A maintainer, member or agent settles it, or a merge goes through while it is open.
- A stale confirm resets to an old tip.
