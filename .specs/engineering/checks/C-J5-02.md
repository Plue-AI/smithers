# C-J5-02 A broken flow merge leaves the previous version Active

Proves: mvp.md §6.12 Pinned versions ("Merged · not active"), J5.3 · spec.md §11.3.0, §11.3.1, §11.3.2, §4.3, §3.1 · Layer: integration · Stage: S1 · Tickets: T-FLW-03, T-FLW-04, T-FLW-11
Automation: `packages/backend/internal/services/flow_load_integration_test.go` (new) and `packages/smithers/agent/registry/test/ExecutableRefresh.test.ts` (case "edit breaks an existing flow") · Runs in: CI

## Setup
- Real PostgreSQL 18 with migrations at head; fake GitHub server; test process runtime for the ephemeral machine (process mode is test-only).
- Repository `main` at commit M1 with a valid `flows/todo/flow.ts`; `flow-load` has run and `todo` is Active at digest D1.

## Steps
- FLW11 QA G17: keep a D1 TODO held across a failed load and later D2 activation. Edit its imported helper/review module/lockfile in the guest working copy, rebase, restart and Resume/ordinary Retry through the immutable resolver. Admit another TODO after D2 activation. Test-only explicit D1/D2 blob fixtures remain a separate pre-activation suite.
1. Push M2 to the fake GitHub `main`: `flows/todo/flow.ts` with a type error in one step.
2. Let the poll scheduler observe M2. Wait for the `flow-load` run to finish.
3. Read `workflow_definitions` and the `flows` durable stream.
4. Admit a new TODO.
5. Push M3 that touches only `src/index.ts`, which no flow imports. Wait for its load.
6. Push M4 that fixes the type error. Wait for its load.
7. Push M5 that changes only `lib/todo-steps.ts`, a helper `flows/todo/flow.ts` imports from outside `flows/`. Wait for its load.
8. Push M6 that changes only `pnpm-lock.yaml`. Wait for its load.
9. Push M7; while M7's load runs, push M8 and then M9. Wait for the loads to finish.
10. Registry unit case: load flow X, rewrite it invalid, call `refresh.flow("X")`.

## Pass when
- T-FLW-11's built-in resolver uses explicit immutable digest/blob plus imported review and dependency environment. Held/restarted/resumed/ordinary retried work still loads D1 bytes, with one TODO run per attempt; only new admission or Retry-current pins D2. A failed load changes neither old run nor Active pointer.
- The integration receipt distinguishes test-only immutable-blob fixture coverage from real loader/activation acceptance, which is joint with C-J5-01/T-FLW-03/04.
- Exactly one `flow-load` run exists for M2. M3's load writes no `workflow_definitions` row and leaves activation unchanged.
- `workflow_definitions` has a row for `todo` at M2 with status `failed` and a `load_error` that names the file and line.
- the newest loaded `workflow_definitions` row for `todo` is still D1 after step 2, in the same transaction as the M2 row's insert.
- The `flows` projection shows `merged-failed` with the error text, and a delta with that state carries its durable-stream cursor.
- The TODO admitted in step 4 pins D1 when it enters Starting.
- After step 6, `todo` is Active at the M4 digest, and D1 is `previous`.
- After step 7, `todo` has a new `loaded` version at M5 with a new digest, and it is Active.
- After step 8, every overridable flow has a new version at M6 whose execution digest is unchanged and whose lockfile digest is new, and each is Active.
- Step 9: loads run at M7 and M9 only; none runs at M8.
- Step 10 returns `Refused`; `catalog.executables` still holds X at its first digest; `catalog.refused` names X.

## Fail when
- A branch-loader stub or mutable working-copy import changes old work, a coding phase creates a second TODO run, or an injected D1/D2 test is counted as real activation.
- Active becomes empty or switches to the M2 version (today's behavior at `Executable.ts:2036` drops the previous entry).
- The error is only logged, so the Flow card shows Active with no failure.
- A failed load writes no row, a load whose digests already exist writes a row, or a helper or lockfile change outside `flows/` leaves the old version Active.
