# C-J2-02 The `todo` label freezes revision 1, ignores later edits and deduplicates deliveries

Proves: mvp.md J2.2, §6.3 (label row), M-16 · spec.md §3.2, §10.2.1, §10.2.1a, §10.4.2, §12.3 (issue labeled `todo`) · Layer: integration · Stage: S1 · Tickets: T-STK-09
Automation: `packages/backend/internal/services/todo_label_db_test.go` (new) · Runs in: CI (real PostgreSQL; the fake GitHub REST server with issue events and ETags)

## Setup
- Issue #6 with initial body B6, authored by a member.

- Product schema at head; members Will (owner) and Ben (Member) with `push` on the fake repository.
- Issue #5 titled "Retry webhooks" with body B1, authored by Alice (a member).
- The issues poll stream enabled against the fake server, and webhook deliveries that request a fetch of that stream.

## Steps
1. Ben applies `todo` to #5 (label event E1). Deliver the webhook.
1a. Ben applies `todo` to #6 and edits its body to B6′ before the next poll.
2. Read the TODO and its revisions.
3. Edit #5 to title "Retry webhooks v2" and body B2. Deliver the `edited` webhook and run one poll.
4. Redeliver E1 three times: webhook, poll, webhook.
5. Run 10 engine passes while the TODO is `queued`, then admit it and edit #5 again to B3.
6. Read the prompt the run receives (§10.4.2).
7. Ben removes `todo` from #5 and applies it again (label event E2) while the TODO is unmerged.
7a. Drop #5's TODO. Within one 120 s window Ben removes and reapplies `todo` on #5.
8. Race two production issue-poll consumers and a session Make TODO commit for the same issue. Crash before admission commit, after commit before cursor advancement and after remote label/comment success before acknowledgement; restart and replay.
9. Invoke the registered production migration after T-STK-14 over literal skipped, backfilled member-work and unknown-null fixtures. Repeat after resolving the unknown row through the approved backfill.

## Pass when

- Step 8 commits event/request receipt, TODO, revision/context, placement, projections and outbound intents together under per-issue serialization. No cursor advances beyond uncommitted consumption. Races and recovery create one active unmerged TODO and no duplicate effective label/comment. A dropped-then-relabelled issue can create a new TODO while the old TODO and issue history remain intact.
- Step 9 aborts on every unclassified or member-work null todo_id before deleting rows or setting NOT NULL. Only verified unadmitted skipped rows are deleted. Backfilled TODO/branch/member-commit and retained PR number/head identities survive unchanged; recorded migration checksums are not rewritten.
- Step 1a: revision 1 of #6's TODO holds B6′ (the first read after the label event, §10.2.1a), and the TODO card shows it with the read time.
- Step 7a: one new TODO from the second `labeled` event; the cursor hands each event over once.

- Step 2: exactly one TODO; revision 1 has prompt = "Retry webhooks" + B1, reason `from-issue`, the `issue_digest` of that text and actor Ben; appended last in the stack; `fixes_issue = true` (§10.2.1).
- Step 3: no new revision; prompt and `issue_digest` unchanged.
- Step 4: still one TODO and one `placed` event; the label stays on the issue.
- Steps 5-6: the run's prompt is revision 1's text; B2 and B3 never appear in `todo_revisions` or the run input.
- Step 7: no second TODO, since an issue has at most one unmerged TODO (§10.2.1).

## Fail when
- An edit before the TODO starts replaces the prompt (today's `ObserveIssue` "not started takes new text", `mythical_items.go:236-262`).
- A redelivery creates a second TODO or a second `placed` event.
- The poll and the webhook race into two TODOs (no unique key on `(issue, label event id)`).
- A new label event on an issue with an unmerged TODO creates a TODO.
