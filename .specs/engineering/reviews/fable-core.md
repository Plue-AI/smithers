# Fable review: engineering core docs (2026-10-02)

Reviewed: `overview.md` v0.3, `spec.md` v0.3, `delta.md` v0.3 (re-read after its 13:21 edit), `tickets/README.md`, `checks/README.md`, against `mvp.md` v2.4 and `main` at `0688fd5980`. Individual ticket and check files were not reviewed (being edited). 52 delta.md claims were checked against code (last section).

## Verdict

**Needs fixes before Will approves.** The target architecture is sound and the deferrals match mvp.md §16 (nothing deferred is built, except `FAN_OPEN` monitoring that only serves a deferred feature). Three problems must be fixed first:

1. **The attribution mechanism cannot be validated by its own spike (F-01).** fanotify never reports a uid, and async events for short-lived writers (`sed -i`, `mv`, `cp`) race the `/proc/<pid>` lookup. C-SPK-01 as indexed ("reports the writer pid and uid") would pass against long-lived writers and still leave J3.4 attributing bursts to "system".
2. **Stage 1's one long-lived `todo` run (T-FLW-11) sits on a stage-2 machine lifecycle (F-02).** Today an agent workspace idles out after 5 min and its disk is reclaimed after 24 h; sleep/capture/wake is S2. A PR reviewed more than a day after it opens loses its working copy in the S1 dogfood that M-31 starts.
3. **Setup contradicts itself on where the GitHub App callback lands (F-03)**, and relies on a GitHub API that doesn't exist to add callback URLs later.

Plus 9 major findings: the app agent still dispatches from the browser with a bearer in JS memory (breaks branch-shared conversations), no wake-reconcile after an asleep-branch rebase, per-viewer fields inside shared projection topics, a thin-path estimate that is 3–7× under its own ticket sizes, two W0-grade spikes placed in stage R, and a delta row that marks a P0 behavior as kept when the code discards it.
