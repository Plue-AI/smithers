# T-GH-09 Outbound writes: keys, per-target order, supersession and reconcile

Stage S1 · Size M · Depends on T-GH-01, T-STK-01, T-GH-02, T-GH-14, T-ACC-03, T-STK-07, T-STK-12 · Unblocks T-FLW-09, T-FLW-11, T-GH-03, T-GH-05, T-GH-06, T-MNT-01, T-MNT-03, T-REL-02, T-STK-04, T-STK-09, T-STK-16 · Issue: [#3520](https://github.com/smithersai/smithers/issues/3520)

## Goal
Killing the host at any point during a GitHub write leaves exactly one PR, comment, label, merge, close or pushed head on GitHub after restart, because every write is keyed before the call and looked up by key before any repeat. Writes to one target keep their order, a newer decision supersedes an unsent older one, and reconcile never replays a write that a newer action on GitHub has overtaken.

## Scope

- Include issue creation and check-run create/update in the keyed adapters. Route every installed GitHub writer through the outbound module, including filing TODO issues, landing pushes/PR creation, mirror pushes and check-run lifecycle writes. Machine proxy writes are not an alternate authority path: refuse generic POST/PUT/PATCH/DELETE from machines before token issuance or remote dispatch, including PR, ref and check-run endpoints. Authorized product writes use host keyed adapters and their command gates. Checks: C-GH-09, C-DUR-03, C-SEC-03.

- Build keyed adapters with fixed write fixtures. UpdatePullBody, ready/draft and ClosePull caller integration belongs to each caller's ticket. The merge adapter requires a bound session approval and an injected dispatch/recovery gate using T-STK-04's production `DecideMerge`; before that caller lands, merge dispatch fails closed. Conflict outcomes are persisted for later inbound dispatch and hold further branch pushes until resolved. This avoids a dependency cycle with T-STK-04 and T-GH-06. Check: C-GH-09.

In:
- Lands before T-ACC-05 (tech lead 2026-10-02, edge cut): Implement keyed writes and their production callers with a single internal merge-authorization provider. Default provider is **RefuseUnavailable**: no merge intent creation, approval lookup that assumes a missing table, token issuance or PUT /merge when confirmation/DecideMerge wiring is absent. Boot recovery may look up an already-sent merge with host read credentials and settle independently proven completion; it cannot send/retry or synthesize approval. Preserve unresolved intents for the real provider. - §10.4.4 accepted-proposal receipt replay reports existing outbound status and never creates another write decision. §10.7.2 Drop compensation persists before PR number discovery; close-after-reconcile is keyed to the Drop event and survives lost responses. Check: C-STK-06.
- The write kinds of §12.4.1: open PR (title = TODO title), update the PR body, mark ready or draft, push, merge, close a PR on Drop, close an issue on merge, add a label (with its "Committed as Tn" comment), revert a label, and comment. Each is recorded in `outbound_writes` with state `intended`, in its own committed transaction before the call, with `target`, `field`, `desired`, `precondition` and `seq` (§12.4.1).
- Keys `<kind>:<target>:<revision>`: `pr:<branch>`; `body:<pr>:<body digest>`; `ready:<pr>:<event seq>` and `draft:<pr>:<event seq>`; `push:<branch>:<intended head>`; `merge:<pr>:<reviewed head sha>`; `close-pr:<pr>:<event seq>`; `close-issue:<issue>:<event seq>`; `label:<issue>:<label>:<event seq>`; `unlabel:<issue>:<label event id>`; `comment:<subject>:<purpose>:<revision>`. The event seq is the `todo_events` sequence, attention id or confirmation id of the action that asked for the write, so a TODO that is reopened and dropped again gets a new close key.
- Order (§12.4.1a): writes to one target are sent one at a time in `seq` order. A write starts only when every earlier write to its target is `done`, `superseded` or `conflict`. For every write kind, Write() commits `intended` → `unknown` before the external call. Only `intended` is unsent; `unknown` is potentially sent and must be looked up after restart. A response that does not arrive leaves the row `unknown`. Check: C-GH-09, C-DUR-03.
- Supersession (§12.4.1a): recording a write marks every earlier unsent row for the same target and field `superseded`, and that row is never sent. Comments and merges are never superseded by newer queued writes. A merge with failed authorization/readiness or a prior external containment fold settles `superseded` (§12.4.1b); retained approvals do not authorize a new automatic retry.
- Reconcile (§12.4.1b), at boot and before the next write to a target, per kind: open PR by head branch (`FindPull`); comment by the marker `<!-- smithers:<key> -->`, searched with `since` = the key's record time minus 1 min; body by digest; close, ready, draft and labels by the App's own events on the target since the row's `created_at`, then the current value against `desired` and `precondition`; merge by `GET /pulls/{n}`, never repeated after one succeeded; push by `git ls-remote`. A value that matches neither `desired` nor `precondition` settles `conflict` and hands the change to the §12.3 mapping (for a push, `foreign_push`, T-GH-06); nothing is written over it. Repeat once under the same key only when the kind-specific §12.4.1b preconditions still hold. At boot, recover unsent `intended` merge intents as well as `unknown` ones. Before any initial or repeated merge send, require the recorded session approval, current approving-member authorization and a fresh `DecideMerge` under this operation's verified fence; exclude only that matching fence, never a competing one. Claim potentially sent work durably before the call so a crash recovers it by lookup as `unknown`. Failed conditions settle `superseded` and retain the approval receipt; recovery never fabricates a session or approval. Check: C-GH-09, C-STK-07, C-ACC-02.
- States (§3): `intended`, `unknown`, `done`, `superseded` and `conflict`, with `settled_by` (`response`, `event`, `state` or `lookup`) and one recovery receipt per reconciled row.
- Attribution in the written text (§12.4.2): "Requested by @owner"; actions taken for a person read "by @ben via Smithers".
- One outbound module used by every GitHub writer in the host. The proposal `PendingOp` mechanism folds into it.

Out: merge approval creation or automatic replacement; the merge route/readiness predicate (T-STK-04); inbound foreign-push mapping (T-GH-06); repository shell/check/flow execution on the host; card Views and public command changes; reconcile of run steps (push, GitHub write and shell) inside the flow runtime (T-FLW-09, S2); non-GitHub side effects; webhook delivery dedupe (T-GH-02); the PR body's content (T-GH-03).

## Changes

- For every kind, Write() commits the send claim `intended` → `unknown` before calling the external adapter. This applies to first sends and permitted retries. Recovery distinguishes unsent intended rows from potentially sent unknown rows; it never repeats unknown work without lookup. Supersession applies only to intended rows. Checks: C-GH-09, C-DUR-03.

## Risks and notes
- Risk: a person who quotes the marker in a later comment could make a lookup settle on the wrong comment. Confirmed by a fault-test case where a member's comment carries the marker. The lookup must match `performed_via_github_app.id` to T-GH-14's canonical install App id, not merely today's check for any App and a Bot (`findComment`, `:452–478`). A person's comment or another App quoting the marker cannot settle this install's write. Check: C-GH-09.
- Resolved by supersession (§12.4.1a): an older unsent body write is `superseded`, and an older sent one is reconciled before the newer one is sent.
