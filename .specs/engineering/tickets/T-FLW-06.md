## Goal
After each merge, a background learning run writes source-linked decision pages to the wiki and evidence-backed proposals, the merged TODO shows "N lessons", and a proposal becomes a TODO only when a member selects Make TODO.

## Ownership (Will, 2026-10-02)

Design (smithers-06) builds every visual component and its styles: `ProposalCard` view and the lessons receipt on a merged TODO. Engineering wires them: the learning flow, `proposals`, accept and dismiss. The seam is the card's view-model schema (spec §14.2.1, the consuming card ticket). Design builds against it with fixture stories, and engineering doesn't edit components or CSS.

## Security preconditions
- Repository learning code, imported modules and mining/model work run only as the unprivileged coding user inside an ephemeral machine (M-29, §1.3). Pin the Active version from trusted main; bind run reads and returned output to its stored repository/TODO/run. Treat reviews, steers, diffs and source as untrusted data; proposed diffs are quoted context, not executable patches. Provider keys stay on the host. smithers-3f reviews, with smithers-38 reviewing typed output. Checks: C-J8-01, C-J5-03, C-SEC-02.
- This ticket adds no root step. Its inherited launcher consumes the R1–R3 inputs inventoried in T-SEC-01, summarized below; those inventories and the T-FLW-01 packaged-artifact gate apply on fresh and retained machines. Branch/member inputs block launch until the named production C-SEC-02 tests prove validation before root use. Branch-built code is never installed or executed by root.
- R1 startup inputs: helper bytes/digest, install script and destination from packaged main; bundle-controlled msb path, environment/PATH/HOME, machine id and deadlines from install state; pinned image/layer, base shell/Python/hash/file tools, search/import paths, helper/temp/parent entries and upstream OCI metadata/blobs from the installed image and registry. Retained snapshots/cache/environment can contain branch/member entries. `TestGuestHelperInstallPinsInterpreterAndEnv` validates provenance, ancestors and replacement resistance.
- R2 setup inputs: login/UID/directories, HOME_LINKS/GO_SETTINGS and helper from packaged main or host-bound account allocations; passwd/group, useradd/shell and home identity from image/account state; env.json keys/values and tool-cache targets from main code plus branch toolchain selection; cache/home names, files, ancestors, symlinks and ownership/modes from branch/member retained state; filesystem responses from the guest kernel. `TestRootSetupNeverFollowsMemberSymlinks` validates allowed values and no-follow writes.
- R3 supervision inputs: request id, fixed identity, transport/terminal settings, exec/cgroup ids and relay endpoints from installed main/host state; argv/env/cwd/root/user/stdin, fs operation/path/content/mode/read limit, request JSON/parents/ownership, symlink graph, capture results, terminal sizes/signals/descriptors and peer bytes from branch/member requests or retained state; startup env/passwd/groups as R1/R2; cgroup files/process population and fork/wait/signal/exit/filesystem/network responses from the kernel and guest processes. `TestRootPreflightParsesOnlyEnvelope` proves bounded envelope validation and group/GID/UID drop before payload use. Installed coding artifacts/bindings come only from the approved bundle/catalog digest, proved by `TestRootManagedArtifactInstallUsesApprovedBundleOnly` and T-FLW-01's binding/helper cases in C-SEC-02.
