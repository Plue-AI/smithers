## Goal
With webhooks off or dropped, PRs, checks and `main` reach PostgreSQL within 60 s of the change on GitHub and issues within 5 min. Reshape the existing pollers, shared budget and token cache under spec §12.2 and delta §7; no new scheduler, GraphQL query or request-per-hour cap.

## Scope
In (adopted owner pre-review):
- Commit fetched github_synced_* cache rows, the durable issue-event cursor and pending consumer-delivery records in one transaction. Persist a stable identity per stream/object version or issue event id and consumer. Consumers commit their receipt and effects atomically, then acknowledge delivery; failures and restart retry the same identity. Route every install GitHub request through shared budget admission and accounting, including direct user-repository transports, repository-list reads and installation-token minting. Install startup alone replaces old workers; hosted Plue startup retains its existing workers. Check: C-GH-08.

In:
- Land dark against the T-GH-01 credential/minter, T-STK-01 storage, T-ACC-02 permission-handler and T-INS-02 install-runtime contracts. Until each required provider is available, keep its install poller disabled, make no GitHub request or consumer effect, and report unavailable rather than fresh. Unregistered downstream consumers retain pending deliveries without running a substitute handler. Enable only through production install composition after C-GH-08 proves these guards; hosted workers retain their existing behavior.
- Existing pollers with state in memory, not a new scheduler or state table. Streams, requests and cadences follow §12.2: refs 30 s (`git ls-remote` of `main` and `refs/heads/smithers/*`); pulls, PR state/check reads, review comments and conversation comments 45 s; issues and issue events 120 s; members' permission hourly. Check: C-GH-08.
- PR state and checks: reuse the existing per-open-TODO `follow` loop and `Pull`/`HeadChecks` REST reads (`mythical_items.go:2179`, `mythical_github.go:258,611`), with conditional reads through the shared budget and cache. Reuse existing review reads. No GraphQL query. Check: C-GH-08.
- Issue events (§10.2.1a, §12.2): `GET /repos/{o}/{r}/issues/events?per_page=100`, conditional, paged back to a durable cursor (the largest event id consumed). Every `labeled`, `unlabeled` and `renamed` event is handed to T-STK-09 once, in id order, so a label removed and reapplied between polls is two events, not a no-op. A `labeled` event carries the applier and the event id, which T-STK-09 needs for the §10.2.1 table, the revert and the idempotency key `(issue, label event id)`.
- Every REST read is conditional (`If-None-Match` with the stored ETag). The `since` and event-id cursors stay at the newest value seen, so an unchanged repository repeats the same URL and gets 304. A page beyond the first is fetched only when every row of the first page is newer than the cursor.
- Installation tokens, scoped ones included, are cached per (installation, permission set) until 5 min before expiry (§12.2.1).
- Budget (§12.2.2): reshape the existing `BudgetTracker` in `github_budget.go` into shared admission/accounting for every install GitHub API call, using response headers and conditional REST reads. Below 20 % of a resource's `X-RateLimit-Limit` remaining, issues, issue-events and members' permission cadences double until `X-RateLimit-Reset`; other cadences stay unchanged. A 403 or 429 with `Retry-After` pauses only that stream until `retry_at` and records `limited` for health. No new hourly request-count model or cap. Check: C-GH-08.
- One typed GitHub error, `{permission | not_installed | rate_limited(retry_at) | unreachable}`, carried as the §6.2.3 envelope class `github`.
- Changed objects are written to the existing `github_synced_*` store, the one GitHub cache (§3.0), and handed to their consumers through one dispatch interface. Consumers: `main` moved → main pull (T-GH-07, T-GH-07) and the flow load (T-FLW-03); pull/check reads PR state and head → T-GH-03, T-GH-06; pull/check reads reviews and the comment streams → T-GH-04; pull/check reads checks → T-GH-03; issues and issue events → the issue card and the `todo` label path (T-STK-09); permissions → T-ACC-02.
- Webhooks (§12.2.4): a signed delivery triggers an immediate fetch of its stream. No cadence ever stretches, so a dropped delivery costs no freshness. Payloads never become state.
- A Retry hook that immediately makes every stream due, subject to in-memory `retry_at` and shared budget admission (T-GH-07 exposes it). Check: C-GH-08.

Out: health states and `/api/github/sync` (T-GH-07); inbound effects (T-GH-04..07, T-STK-09); outbound writes (T-GH-09); webhook delivery setup (optional, §12.2.4); per-PR polling of review comments or conversation comments; new GraphQL queries, schedulers, sync tables and hourly request-count models; executing fetched repository code or its hooks/credential helpers; root steps and machine provisioning; card View or retained Issue/Issue-list renderer/schema changes; replacing Plue workers outside the install composition.

## Risks and notes
- Risk: a cursor set to "now − cadence" changes the URL on every poll, so no request ever gets a 304. Confirmed in C-GH-08 when the 304 ratio of an idle hour is below 90 %.
- Risk: charging 304 responses locally defeats conditional-read savings. Confirmed when `TestInstallPollingCadencesAndBudget` records a charged debit for an unchanged conditional response; smithers-3f approves the accounting contract.
- Risk: the 45 s cadence leaves 15 s for fetch and projection. Existing REST reads that exceed it fail C-GH-07. smithers-8a decides cadence or budget changes; Will decides changes to product freshness targets. Do not tune locally.
- Risk: paginated REST check/review reads omit later pages. Exercise literal multi-page fixtures through existing readers; smithers-3f decides paging changes and C-GH-07 verifies freshness.
- Durable delivery records and consumer receipts reuse existing storage and commit paths under §19.4; no new sync table. smithers-3f approves the storage encoding; smithers-8a decides any schema reservation under C-PRC-02. No new table is authorized here.
- Risk: `git ls-remote` every 30 s may meet git-side throttling. Confirmed by HTTP 429 from `github.com` git endpoints during C-GH-07.
- Ownership: §12.2 lists the members' permission poll as a stream, and §5.1.3's hourly re-check belongs to T-ACC-02. This ticket schedules it under the shared budget; T-ACC-02 owns the handler.
