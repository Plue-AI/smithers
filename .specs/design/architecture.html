01

Layers: Paper tokens up to catalog commands, and who owns each

#layers
  • Design builds every visual piece; engineering wires data and actions (Will, 2026-10-02).
  • The seam is one zod view model per card, packages/rpc/src/<Card>Card.ts (T-APP-19). Until it lands, Views build against ui-components.md with local fixtures. Local fixtures are provisional; acceptance uses T-APP-19 schema fixtures.
  • A View exists only for a spec.md §14.3 row. Retained cards (Issue, PR, Review findings, Wiki, flow Form) keep their schemas.

02

The View/Container seam: data comes in as props, gestures leave as catalog tags

#seam
  • A missing action means no button; a missing gesture does nothing. The Container filters actions[] and gestures for the viewer; the View never decides who may act.
  • Tags are opaque. The View hands back action.tag with {...action.args, ...input}, and the control carries data-flow={action.tag}.
  • Handler 3 never leaves the View: roving tabindex, Escape to close, controlled inputs, disclosures that don't persist, Copy.
  • A field the View needs but the props lack is a spec change. Raise it with the tech lead (8a), who updates spec.md §14.3, ui-components.md and T-APP-19 together.

03

Shell anatomy: one conversation per branch, a timeline rail on desktop, pills on narrow screens

#shell
  • Everything embeds in the conversation. Nothing opens full screen unless the person maximizes it (EMBED LAW).
  • The timeline is desktop only. Hiding a notice preserves the entry; any still-applicable action remains available.
  • UI-only flows (theme, open, maximize, navigate, palette, filters) change only the screen of the person who ran them, even when their app agent ran them.

04

Card anatomy: header, body, one actions row, and one entry per thing

#card
  • A View renders only the actions it is given. Stop is refused while a question or approval wait is open (spec.md §10.7.1), so this card has none.
  • One solid button per card, for its primary act, with ghost buttons before it.
  • One persistent entry per entity, keyed (kind, id). Showing it again jumps to that entry (spec.md §14.5.1).
  • Header slots are presentation only: they show model fields and add none.
  • A reason replaces the button it blocks, as text. An Action with disabled.reason renders that way.
  • Card body lines hold 12 words or fewer, in product words only.

05

Identity: every participant has one mark, wherever it appears

#identity
  • People are circles; agents, Smithers included, are rounded squares.
  • Every agent doing work is its own participant with a stable id: Smithers, Claude Code, the coding agent, reviewers (M-34). It never collapses into the person's avatar.
  • An agent acting for a member, Smithers included, takes that member's color and reads “Claude Code for Ben”. Plain “Smithers” in ink marks install events (system), never an agent.
  • Only a person's own doors keep their circle, with a small badge: “Maya via SSH”, “Ben's terminal”, “Ben via CLI”.
  • color_index: 0–5 a member's color, also for anything acting for them; 6 an agent acting for nobody; 7 neutral, for GitHub users and outside writes. Tokens per index: #color.

Source mvp.md §3.1, §6.8 (Presence, External changes), M-21, M-27, M-32, M-34; settled ruling on M-34 marks (2026-10-02); spec.md §7.3.1, §7.3.2, §14.6a.1; ui-components.md v0.4 Actor, T-UI-01; mock parts.tsx (Avatar, actorName, flagName), world.ts (isSmithers, forWhom, via), mock.css (PORT · avatars), css/code.css (flags).

06

Color semantics: fixed status colors, and actor color as a separate channel

#color
  • Status colors have fixed semantics: live is teal, attention is gold, failed is ember; done and quiet are neutral. In review is quiet.
  • Actor color is a separate channel. It says who, never what state, and a status never borrows an actor color.
  • Both themes gate acceptance: every swatch has a light and a dark value.

07

TODO lifecycle: nine states, each with one glyph and one pill

#states
  • Each state has one glyph and one pill, the same on every card, row and timeline line.
  • Merged is done. Learning is a receipt on the merged card (“2 lessons”), never a state.
  • Drawn from mvp.md §4.1 and spec.md §4.1. spec.md's transition table is authoritative and adds rarer edges: a PR reopened on GitHub within 7 days revives a Dropped TODO, and a merge on GitHub counts from any unmerged state.

08

One durable attempt: work stages, system acceptance, then wait

#run
  • One attempt is one durable run of its pinned flow version. It lives until the TODO merges or is dropped; Retry starts a new attempt beside the old one.
  • A machine restart re-runs no finished step: the run resumes, or shows interrupted with Retry (spec.md §19.1).
  • Capture (stack.candidate) and Propose (stack.propose) are system acceptance, not overridable flow steps. The step strip keeps its labels.
  • After Propose the run holds at the wait for merge. The wait needs no machine: the machine is released once safe-idle, and its slot stays held until the stop is confirmed.
  • A clean rebase reruns checks only, and the prior review stays (same patch-id). A conflict-resolved rebase or a code change reruns review. Any rebase voids an approval.
  • Phase titles and cell labels are deterministic. ✦ marks what the fast model wrote, only for runs someone inspects.

09

Merge readiness: one decision, read by every merge surface

#merge-rule
  • One rule for every merge surface: no card offers a merge another card would refuse.
  • MergeReady's nine rows run in order. The first failing row's reason replaces Merge, as text.
  • Role and session sit outside MergeReady, in the authorizer. Only required GitHub checks block; machine checks and review count through the accepted generation (row 5).
  • A clean rebase reruns checks only and keeps the prior review (same patch-id). A conflict-resolved rebase or a code change reruns review; an earlier review shows only when its patch-id matches. Any rebase voids an approval.

10

App agent permissions: runs at once, asks once, opens your merge, or has no path

#permissions
  • The app agent acts with the asker's authority and shows as Smithers for that person. It never merges or approves.
  • External agents through the CLI or skill follow the same run, confirm and never rules.
  • Only the asker sees Confirm; others see nothing until the shared action receipt.
  • A flow renders the same card whoever runs it, and each run is its own instance. Exceptions: a Confirm card, seen only by its asker, and a Draft, seen only by its author until Commit. Only the actor's mark tells a person's act from an agent's.

Source mvp.md §3.1, Appendix B (legend, B.1, B.2, B.3, B.4, B.6), M-21, M-33, M-34; settled Confirm ruling (product, 16:51, 2026-10-02); spec.md §5.2, §5.3, §5.4, §6.1.2, §14.3 (Confirm, Draft), §14.5.1, §15.1.3, §15.1.5; ui-components.md v0.4 T-UI-05; mock cards/Act.tsx, cards/Confirm.tsx, cards/Draft.tsx, journeys/ask.ts, journeys/agent.ts, world.ts (ask, pressed).
